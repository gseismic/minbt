## 1. 两类接口的判断

|维度|公共用户接口|内部接口|
|---|---|---|
|受众|业务开发者、脚本作者、Agent|模块、调度器、运行时、测试替身|
|核心目标|短、直观、表达业务意图|正确、可维护、可测试、可演进|
|抽象语言|业务对象和动作|状态、协议、生命周期和不变式|
|复杂度策略|高频路径默认化，复杂路径渐进展开|边界完整，不能依靠隐式行为|
|可变性|需要版本兼容|允许重构，但依赖方契约必须清晰|
|错误|可执行的修复提示|可程序化判断、传播和清理|

评审每个公开参数时，回答：它是否表达用户真正关心的业务选择？如果只控制缓存、归并、连接、调度或内部字段路径，应移到内部配置或自动处理。

评审每个内部类时，回答：它是否拥有跨方法的状态、资源、不变式或多个真实实现？如果只是把一段函数调用重新命名，保留为方法、局部结构或私有元组。

## 2. 场景模板

为每个场景填写以下内容：

```text
场景名称：
使用频率：高 / 中 / 低
用户目标：一句业务语言
最短调用：
输入形状：
输出或状态变化：
必须显式表达的风险：
缺失、重复、冲突和空数据行为：
资源与重复运行行为：
验收断言：
```

建议至少包含下列场景：

1. 最小成功调用：默认数据、默认配置、一次成功结果。
2. 多实体调用：多个账户、商品、文件、记录或市场使用同一接口。
3. 单实体特例：确认不需要另一个单数 API。
4. 字段/格式差异：输入字段叫 `value`、`last_value` 或领域自定义名称。
5. 多来源联合：不同来源提供不同实体，或同一实体出现重叠。
6. 空和错误输入：空区间、缺列、非法值、乱序、重复和错误路径。
7. 大数据和资源：逐行读取、分页、迭代器、连接、缓存和提前终止。
8. 迁移调用：旧接口、目标接口和混用期间的行为。

对每个场景比较代码长度、需要记忆的概念数量和失败信息。不要只比较类数量；一个名称不清晰的“万能入口”可能比四个领域入口更难使用。

## 3. 公共接口模式

### 3.1 领域入口优于万能事件

当库正式支持少量稳定领域类型时，为每种类型提供有意义的入口，例如 `set_records`、`set_orders`、`on_records`、`on_orders`。保持相同的载荷规则和时间语义。

不要把所有类型塞进：

```python
on_event(kind, payload)
on_data(kind, payload)
on_item(item)
```

只有在类型集合确实开放、调用方必须自行路由、且聚合/重复/错误语义对所有类型一致时，才采用通用事件协议。否则，通用 `kind` 会把类型判断、载荷形状和错误处理转嫁给每个用户。

### 3.2 字段映射优于强制标准字段

用 `field_key`、`date_key`、`id_key` 或显式映射适配来源格式：

```python
library.set_records(rows, value_key="last_value")
```

这表示 `last_value` 是参考值，但不要求把字段重命名成 `value`，也不要求存在并不适用的 `close`、`amount` 或 `name`。

区分三件事：

- 结构字段：为了定位记录或推进状态必须存在，例如时间和实体标识；
- 业务字段：回调中原样保留，用户自行解释；
- 参考字段：由 `*_key` 指定，缺省时只给常见格式一个便利默认值。

默认字段名必须写清“只是默认值”。切换 `value_key` 后，不应继续隐式读取旧字段、合成别名或改变用户原始数据。

### 3.3 单数是复数的特例

统一让回调载荷使用 `id -> record`、`id -> records` 或同构集合。单实体时只包含一个键，不增加 `record`、`on_record`、`get_one` 等平行路径。

这样可以让策略、批处理和测试从一个实体自然扩展到横截面；内部也只需维护一套归并、冲突和状态更新逻辑。

### 3.4 默认值与显式语义

为不改变业务结果的常见细节提供默认值；对下列行为要求显式配置或显式方法：

- 删除、覆盖、持久化、发送请求和权限变化；
- 选择参考值、时序、成交/计算时点和重试策略；
- 可能造成数据丢失、账户变化或跨对象污染的操作。

避免布尔参数承载多个语义。使用具名方法、枚举或结构化选项表达选择，并在签名中保持参数顺序一致。

### 3.5 最小扩展协议

高级来源只声明无法从对象推断的内容，例如：

```python
class MySource:
    name = "history"
    data_type = "records"
    value_key = "last_value"

    def rows(self):
        yield {"dt": ..., "id": "A", "last_value": 1.0}
```

要求行顺序、生命周期和字段契约；不要同时要求 `Event`、`Cursor`、`Adapter`、`prepare`、`close`、能力位和优先级，除非每一项都有独立使用场景。资源可以由生成器在 `try/finally` 中管理，调度器负责关闭支持 `close()` 的迭代器。

## 4. 内部架构模式

### 4.1 保留不变式，不保留实现名词

如果系统必须先收齐同一时间点，再批量更新所有账户或实体，那么“不允许部分更新”是必须保留的不变式；`TimeBatch` 这个名字和类并不是必须的。

优先采用以下结构：

```python
for dt, source_rows in rows_by_time(sources):
    data, references = collect_and_validate(dt, source_rows)
    update_state(dt, references)
    dispatch(dt, data)
```

只有当时间片需要在多处长期持有、提供独立 API、拥有资源或被多个实现共享时，才提取值对象。

### 4.2 一个状态只能有一个明确所有者

任何持续状态都应能回答“谁写入、何时生效、谁读取”。对于同一实体的参考值、当前状态或缓存：

- 允许多个来源提供不同实体；
- 同一实体的重复来源默认失败；
- 不用注册顺序、回调顺序或最后写入覆盖来消除歧义；
- 如果确实要切换来源，使用显式切换配置或独立运行，不隐藏在合并逻辑中。

一次操作产生的临时值不能未经说明地变成后续持久状态。例如本次成交价、临时覆盖值和测试注入值只影响本次操作，除非接口明确命名为更新参考状态。

### 4.3 数据层与业务状态层分离

来源层负责读取、时间/标识归一化和字段映射；业务状态层负责账户、订单、缓存或工作流状态；调度层负责顺序与一次性分发。不要让状态对象重新解析来源字段，也不要让来源对象修改业务状态。

分层不等于堆叠类。三个职责可以由一个主循环调用三个小方法表达；只有状态边界和错误传播需要独立协议时才拆分模块。

### 4.4 同类数据一次分发

多个来源提供不重叠实体时，先合并成一个完整类型载荷，再调用一次类型回调。禁止同一时间点因来源数量增加而重复调用用户逻辑。

同类数据重叠时，在状态更新和回调之前失败。新闻、日志等允许拼接的类型应定义稳定顺序，并把来源标识作为业务字段或显式元数据提供，而不是由内部名称偷偷注入。

## 5. 错误、状态与资源

### 5.1 错误决策

|情况|默认行为|
|---|---|
|调用参数或记录结构错误|`TypeError` 或 `ValueError`，指出字段和记录|
|时间/顺序/重复/来源冲突|在状态更新前失败，列出来源、实体和时间|
|业务规则拒绝|返回可检查的结果对象或业务状态，不伪装成成功|
|资源/系统故障|保留根因，补充操作和资源上下文|
|暂时可恢复故障|只有在契约允许时重试，并说明次数、退避和幂等性|

不要让调用方解析自然语言来判断成功。错误消息面向人，状态码、异常类型或结果字段面向程序。

### 5.2 生命周期

至少写清：

- 构造后是否可直接调用；
- `run`、`reset`、`close` 是否可重复；
- 空源、一次性源和不可重放源的行为；
- 回调异常时是否继续、终止或回滚；
- 哪个层级负责释放迭代器、文件、连接和临时文件。

如果重复调用会累积订单、缓存、状态或外部副作用，禁止把它写成看似幂等的方法；改用明确的 `append`、`replace`、`reset` 或新对象。

### 5.3 性能边界

说明时间复杂度、峰值内存、单批上限、阻塞行为、拷贝/视图语义和大记录处理方式。不要为了理论上的无限扩展把所有用户接口设计成异步、流式或可插拔；先保证高频路径可验证，再提供高级来源。

## 6. 迁移模板

使用以下表格描述重构：

|当前接口/行为|目标接口/行为|影响|迁移方式|移除条件|
|---|---|---|---|---|
|旧入口|具名入口|调用方代码|替代示例|版本/日期|
|隐式覆盖|显式冲突错误|数据准备|预先合并或禁用来源|全部调用迁移|
|强制字段|字段映射|输入格式|设置 `*_key`|旧字段不再依赖|
|多套回放|单一循环|性能/资源|统一来源契约|结果测试通过|

每条迁移都配一条正例和一条失败例。明确旧行为是否仍然被支持；不要在目标设计中同时写“删除”和“永久兼容”。

## 7. 反模式

|反模式|表现|修正|
|---|---|---|
|内部实现泄露|用户需要理解 Cursor、连接池、缓存键、批次类|隐藏实现，只暴露业务语义和必要约束|
|万能事件逃生口|所有数据都走 `kind/data`，用户自行分支|固定稳定类型用具名入口，扩展另设高级协议|
|字段强制统一|所有数据必须有一个并不适用的标准字段|使用字段映射；仅要求真正不可缺的结构字段|
|静默优先级|最后写入、注册顺序或回调顺序覆盖状态|冲突失败，或提供显式所有权配置|
|单数/复数双模型|`on_record` 和 `on_records` 各自维护|单数作为集合中的一个元素|
|时间逐项更新|同一时间点按实体更新完整账户多次|先收齐，再一次批量推进|
|未来驱动抽象|为可能的类型、模式、插件预留多层类|先实现真实场景，重复需求出现后再抽象|
|假简洁|一个布尔值或魔法默认值隐藏关键时序/副作用|关键语义显式化，普通细节才默认化|
|错误吞噬|异常变成 `None`、空结果或 warning|在正确性边界失败，提供修复信息|

## 8. 最终评审清单

### 用户接口

- [ ] 能否用一句业务语言解释每个公共概念？
- [ ] 最短成功示例是否足够短？
- [ ] 单实体是否自然落入多实体模型？
- [ ] 高级配置是否没有进入入门路径？
- [ ] 字段映射是否保留原始业务字段？
- [ ] 关键结果、时序和副作用是否显式？
- [ ] 是否删除了只为内部通用性存在的公共入口？

### 内部接口

- [ ] 每个状态、资源和不变式是否有唯一所有者？
- [ ] 是否在正确的边界一次性批量更新？
- [ ] 是否可以用函数、映射或私有记录替代新增类？
- [ ] 输入、输出、错误传播和生命周期是否明确？
- [ ] 重复、冲突、乱序和空数据是否在正确位置失败？
- [ ] 性能、内存、阻塞和拷贝语义是否可验证？

### 交付物

- [ ] 设计文档区分当前实现、目标设计和迁移状态。
- [ ] 典型场景、签名、示例、测试和实现使用同一命名。
- [ ] 迁移表覆盖删除、重命名、默认值和语义改变。
- [ ] 至少有顺序无关、冲突、缺数据、资源异常和重复运行测试。
- [ ] 设计评审后仍能说清“哪些概念明确不引入”。
