# 通用库设计准则

## 目的

将模糊的库设计目标转化为可使用、可验证、可演进的公共接口与最小内部架构。优先保证用户可以用少量、贴近业务语言的代码表达真实意图，再为正确性、性能、资源和兼容性建立足够而不过量的内部契约。

## 总原则

先设计用户接口，再推导内部接口。用户接口服务人的心智模型；内部接口服务正确性、边界和维护。不要用内部实现的通用性反过来污染高频用户路径，也不要为了表面的简洁隐藏会改变结果、权限、持久化或外部副作用的关键语义。

保持以下顺序：

1. 观察真实使用场景，而不是先列类和模块。
2. 固定高频场景的公共接口，再定义数据、状态和错误语义。
3. 只引入能承载独立不变式、生命周期或多个真实实现的内部概念。
4. 通过可执行示例、契约测试和迁移表验证设计。

## 设计工作流

### 1. 确定范围与受众

记录库解决的问题、明确不解决的问题、现有用户和二次开发者。区分三类内容：

- 公共接口：需要稳定命名、兼容承诺和用户可理解的错误。
- 高级扩展接口：允许专业用户接入自定义数据、存储或执行方式，但不应成为入门路径。
- 内部接口：可以变化，但必须有类型、状态边界、错误传播、资源所有权和测试契约。

无法判断某项配置是否面向用户时，先按“实现细节”处理，并检查它是否真正影响用户业务语义。

### 2. 从场景开始

列出 5～10 个代表性场景，按频率和价值排序。至少覆盖：

- 最小成功路径；
- 单实体和多实体；
- 常见输入字段或格式不同；
- 多来源或多事件联合；
- 空数据、缺数据、冲突数据和异常路径；
- 大数据、资源释放、重复运行或迁移。

每个场景都写出用户希望看到的最短代码、输入前置条件、结果和失败方式。若场景无法用一句业务语言描述，先收敛问题边界，不要立即增加抽象。

### 3. 固定公共接口

优先设计少量强概念。每个参数回答一个业务问题，命名使用用户语言。为最高频路径提供合理默认值，把必选参数限制在确实无法推断的语义上。

遵循以下规则：

- 单实体是多实体模型的自然特例，不维护两套 API。
- 稳定支持的领域类型使用具名入口或回调；不要让所有内容都落入一个 `kind`、`event` 或动态路由。
- 扩展点采用最小鸭子类型契约或协议；要求名称、类型和读取方法即可，不重复包装相同元数据。
- 字段名不同优先使用 `*_key`、映射或适配配置；不要为了方便内部代码强制用户重命名数据。
- 默认值只能隐藏非关键细节。会改变结果、价格、时序、权限或副作用的行为必须显式表达。
- 同一概念在方法、参数、返回值、错误和文档中保持同名；不要在不同层使用近义词。

使用“最小示例测试”：新用户是否能只读快速开始和接口签名完成第一次成功调用？如果不能，删除不必要的公共概念或把高级选项后移。

### 4. 定义数据与语义

先定义回调/方法收到的载荷形状，再讨论内部存储。声明哪些字段是结构必需、哪些只是业务字段、哪些字段用于状态计算。不要把某个常见字段误写成标准字段。

对每个数据来源明确：

- 时间和标识如何归一化；
- 单实体是否唯一、重复如何处理；
- 多条记录的稳定顺序；
- 缺字段、空值、非法数值的行为；
- 来源字段如何映射到业务语义；
- 多来源重叠、冲突和所有权如何处理。

避免隐式优先级、注册顺序覆盖、最后写入获胜和静默丢弃。不能自动判断的歧义应在进入状态更新前失败，并给出可执行修复建议。

### 5. 保留必要的时间与状态边界

涉及时间序列、批处理、跨实体计算或账户状态时，先判断是否必须在同一时间点收齐数据再推进状态。如果必须，保留“时间点原子推进”这一不变式，但不自动把它命名为 `TimeBatch` 或创建传递层对象。

优先使用一个主循环、普通局部映射和少量小方法表达：读取、归并、校验、更新状态、分发回调。只有当对象需要跨方法维护独立状态/资源、不变式难以集中表达，或出现多个真实实现时，才提取类。

将来源解析、字段提取和业务状态更新分开，但不为每个动词创建 `Adapter`、`Resolver`、`Projector`、`Cursor` 等空壳层。内部边界可以是简单的 `Mapping`、元组、函数或私有记录。

### 6. 明确状态、错误和资源

为状态型对象写出创建、使用、重置、关闭和重复调用语义。说明谁拥有内存、文件、连接、迭代器和缓存，谁负责释放；正常结束、业务异常、用户回调异常和提前终止都走同一清理路径。

区分输入错误、可恢复业务拒绝和系统错误。错误信息至少包含对象/来源、关键标识、时间或操作及修复建议。禁止通过返回 `None`、空列表或 warning 隐藏会改变结果的错误。只有当调用方已有稳定的程序化捕获需求时，才增加专用异常层级；否则优先使用语义明确的标准异常。

显式区分“本次操作的值”和“持续状态的参考值”。例如一次显式成交价、覆盖值或临时参数不能未经说明地修改后续估值、缓存或其他对象的状态。

### 7. 设计演进与迁移

把当前行为、目标行为和迁移方式分开记录。为每个删除、重命名或语义改变提供：受影响调用、替代写法、是否提供短期兼容、兼容结束条件和测试覆盖。

公共接口遵循版本化承诺；内部接口不承诺兼容。不要为了“以后可能用到”保留永久别名、通用逃生口或多套运行模式。新能力先以高级扩展验证，重复出现且语义稳定后再提升为公共接口。

### 8. 验证设计

至少验证以下维度：

- 高频示例的代码长度和可读性；
- 单实体/多实体结果一致性；
- 字段映射不改变业务字段；
- 顺序、重复、冲突和缺数据的失败点；
- 同一时间点的状态原子性；
- 显式值不会污染持续状态；
- 资源在成功和异常路径释放；
- 两种输入方式或两次运行结果一致；
- 文档、签名、示例、测试与实现没有分叉。

## 设计输出格式

根据仓库约定输出设计文档，至少包含：

1. 结论和设计取舍；
2. 代表性使用场景；
3. 稳定公共接口与载荷示例；
4. 数据、时间、状态、错误和资源语义；
5. 最小内部架构及明确不引入的概念；
6. 当前实现到目标设计的迁移表；
7. 验收标准和实施顺序。

使用参考文件中的检查表补充细节。设计状态应明确标为“目标设计/已实施/部分实施”，不要把尚未落地的接口写成当前能力。

## 工作方式

先检查现有代码、文档、示例和测试，再提出目标设计。区分事实、推断和建议；对可能改变公共模型的假设明确标注。只有缺失信息会实质改变接口形状、数据所有权或安全/副作用语义时才询问用户；其余情况采用合理假设并记录。

用户只要求评审或设计时，不擅自修改实现代码。用户要求实施时，先冻结设计和契约测试，再按迁移顺序修改，并在结束后复核公共接口、错误语义和资源边界。
